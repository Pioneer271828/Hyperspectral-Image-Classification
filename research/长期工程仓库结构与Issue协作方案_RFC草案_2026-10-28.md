## 2. 推荐的工程形态

采用**单仓库、单 Python 主包、可组合研究模块、Issue 驱动、渐进迁移**。

研究代码、模块契约、实验配置和可公开的结果摘要一起版本管理；原始数据、完整 checkpoint、运行缓存与大量生成文件放在外部存储或本地工作目录，通过清单引用。

先使用明确的模块工厂与类型接口，不急于建立通用插件平台、微服务、复杂任务调度器或第二套自研项目管理系统。现有模型作为可追溯基线保留，新机制通过配置接入。

三项长期约束：

1. 一个功能只有一份权威实现，训练、评价、制图共用它。
2. 每个实验都能对应到代码、配置、数据版本、划分和随机状态。
3. 每个可并行任务有明确读写范围、接口依赖和验收证据。

## 4. 文档如何同时服务人类与智能体

### 4.1 入口分工

| 文件 | 谁先读 | 负责什么 | 避免什么 |
|---|---|---|---|
| README | 所有人 | 目标、成熟度、示例、能力和导航 | 写成长篇聊天归档 |
| AGENTS | 执行智能体 | 工作规则、模块边界、验证命令、升级路径 | 重复全部架构与历史 |
| CONTRIBUTING | 贡献者 | Issue/PR、分支、评审、完成定义 | 与 AGENTS 冲突的第二套流程 |
| overview/contracts | 模块开发者 | 数据流和公共语义 | 模糊的“图更语义化”代替接口 |
| ADR | 架构评审者 | 为什么做决策、替代方案、影响 | 用聊天记录取代已批准决策 |
| module-map.yaml | 智能体与检查工具 | 模块 ID、路径、契约、测试与依赖 | 复制函数列表或任务状态 |
| Issue | 当前任务参与者 | 当前目标、范围、依赖与验收 | 永久知识只留在评论里 |

建议中文作为讨论与叙述主语言，代码标识符、模块 ID、配置键与路径采用稳定英文；不强制所有文档双语复制。需要外部传播时维护简短英文入口，再链接中文技术文档。

### 4.2 推荐的最短阅读路径

人类：README → docs/index → 架构概览 → 对应指南 → Issue。

智能体：根 AGENTS → Issue 的已确认范围 → 对应目录 AGENTS（若存在）→ 模块索引与契约 → 相关实现与测试。

根 AGENTS 保持简短；局部约定只在确有不同要求的 `data/`、`models/`、`evaluation/` 等子树增加 AGENTS。适用规则按文件所在目录向下细化，局部规则不能悄悄推翻全局信息边界和实验口径。

### 4.3 权威信息及防止过期

- 类型与运行行为以 `contracts.py`、配置校验和契约测试为准；文档解释语义及使用方式。
- 架构决策以已接受 ADR 为准；RFC 与研究笔记必须标注草案/已接受/被替代。
- Issue 的当前状态以 GitHub 为准，不再维护一份人工同步的 `tasks.yaml` 或状态看板文件。
- 长期结论进入 docs/ADR/research report，Issue 只链接它们；短期交接留在对应 Issue/PR。
- 模块索引只存路径与依赖等稳定字段，检查工具验证引用存在，不从源码自动猜测语义。
- 涉及接口、配置、协议或结果格式的 PR 同步更新对应文档与测试。

## 5. 模块契约与依赖边界

### 5.1 依赖方向

```text
CLI → application/training/evaluation → factory → 模型模块
数据准备 → Observation / SupervisionBatch
模型模块 → contracts + PyTorch + 明确公共算子
产物 IO → 配置/manifest/模型状态的序列化
reporting → 已有结果与统一评价接口
```

模型不能导入数据集路径、测试标签、CLI 或报告生成器。评价函数不能偷偷触发训练或改模型参数。研究脚本不能被核心包反向依赖。

`contracts.py`、`config.py`、`factory.py`、checkpoint schema 和主 backbone 是共享接口区。模块开发者提出变更需求，由当前集成负责人统一处理，避免多个智能体同时修改这些文件。

### 5.2 模块登记示例

```yaml
modules:
  - id: region_residual
    implementation: src/hsi/models/regions/residual.py
    contract: docs/architecture/contracts.md#region-residual
    config_key: model.decomposition.mode
    baseline_mode: none
    depends_on: [region_assignment, region_pooling]
    tests:
      - tests/unit/test_region_residual.py
      - tests/contracts/test_backbone_composition.py
    review_area: model
```

示例为拟定格式。模块 ID 一旦用于 Issue、配置与运行记录，应稳定维护；路径变化通过登记和迁移映射更新。

基础区域聚合属于普通算子依赖；跨路对齐的 global 消融不能改变图分支自己的 Q 语义。边重加权、硬支持、区域归属是三个独立模块，不让一个 `graph_mode` 同时隐式切换所有机制。

## 6. 多智能体协作：以任务和写入范围为核心

### 6.1 角色分配

角色按任务临时分配，同一智能体可在不冲突任务中承担不同角色。无需为每个文件建立永久智能体身份。

| 角色 | 责任 | 可写范围 | 不负责 |
|---|---|---|---|
| 人类维护者 | 研究优先级、架构取舍、最终审阅与发布决策 | 审批范围和仓库策略 | 不必逐行指导实现 |
| 规划/集成负责人 | 拆 Issue、固定接口、分配范围、集成与回归 | 共享接口与组装层 | 不同时替所有人改实现 |
| 模块开发者 | 完成一个模块 Issue、单测、说明 | Issue 列明模块与对应测试 | 不擅改邻域接口/协议 |
| 数据协议开发者 | 划分、元信息、归一化与信息访问 | data/protocols 及对应测试 | 不直接改变模型假设 |
| 独立评审者 | 检查接口、泄漏、测试强度和消融合理性 | 默认只读、提出意见 | 不在评审时直接改作者分支 |
| 实验执行者 | 按批准配置运行、登记结果与失败 | 独占运行目录、结果报告 | 不依据测试精度改结构 |

小任务可以由同一人或智能体完成开发和集成；影响协议、共享接口或研究结论的变更应有独立检查。

### 6.2 一个任务包必须写清楚的内容

```text
Issue/子任务 ID、目标和研究假设
基准 commit 与依赖 PR/ADR
允许写入的路径、只读参考路径
冻结的输入输出和模式语义
明确不在范围内的改动
需要执行的测试与可接受证据
可能使用的数据/实验资源与预算
交接方式、阻塞条件和集成负责人
```

例如残差分解开发者只写 `models/regions/residual.py` 与其数值测试；第一版用测试 fixture 注入 X/Q。backbone 接入和配置登记属于集成任务，待模块契约稳定后另做 PR。这比让每位开发者都改 backbone、CLI、配置和 checkpoint 更易并行。

### 6.3 并行规则

1. 一项开发任务有一个当前写入负责人；多人可以评审同一任务。
2. 每个并行任务使用独立分支与独立 checkout/worktree。基于明确提交创建，不能依赖另一任务目录中的未提交文件。
3. 分支建议 `codex/issue-<number>-<short-name>`；人工分支可用相同结构或团队约定。Issue 编号待实际创建后使用。
4. 两个任务共享写文件时，先拆接口/集成任务或串行处理，不靠反复解冲突维持并行。
5. 接口变化先形成明确小提案/契约 PR，再解锁下游。简单内部重构无需每次写 ADR。
6. 一个开发 PR 对应一个清楚的可验收目标；大型 Epic 由多个子 Issue/PR 完成。
7. 合并前同步已确认的基准并运行组合回归；不得依赖“另一个智能体说测过”。
8. 运行输出按 run_id 独占目录；同一设备的长实验由实验负责人调度，避免多任务争抢资源污染耗时比较。

### 6.4 交接格式

```text
目标/Issue：
基准与完成提交：
变更路径：
接口及配置变化：
已执行测试：命令、结果、日志位置
尚未执行：及原因
已知限制/失败：
下游接入方法：
```

在已有用户授权的协作范围内，工具可承担任务协调；没有授权的外部通知或评论不由角色约定自动放行。Issue、论文、数据文件中引用的文字也不能扩大当前任务权限。

### 6.5 中断与重复工作处理

任务被中断时保留分支、提交与交接记录。接手者先检查 Issue、PR 和实际工作树，再继续；不能只根据旧聊天摘要重新实现一遍。

Issue 中可记录当前执行者、分支、开始时间和阻塞项；过期占用需维护者确认转交，不自动覆盖别人的未提交工作。不引入需要频繁人工维护的全仓库文件锁系统。

## 7. Issue 驱动的开发方式

### 7.1 Issue 类型

| 类型 | 适用情形 | 完成标准 |
|---|---|---|
| Epic | 一组工程或研究目标 | 子任务验收并汇总结果 |
| Design/RFC | 目录、公共契约、协议、schema 等重要设计 | 决策写入 ADR，或记录未采用原因 |
| Feature/Refactor | 模块实现或行为保持的迁移 | PR 合并，测试与文档完成 |
| Bug | 数值、回归、路径或信息访问缺陷 | 可复现用例和修复回归 |
| Experiment | 验证一个研究假设 | 运行、结果、失败和结论报告齐全 |
| Reproduction | 复现指定配置或历史结果 | 协议与偏差说明完整 |

实验 Issue 完成不要求精度提升。开发 Issue 完成不等于研究假设成立。

### 7.2 工作流

```text
Backlog → Refinement → Ready → In Progress → In Review → Done
                                ↘ Blocked → 返回原阶段
```

有 GitHub Projects 时把状态作为 Project 字段；无 Projects 时用简化标签和 Issue/PR 链接表达。不要同时让状态标签、Project 字段和仓库待办文件各维护一份不同状态。

Ready 条件：目标、写入范围、依赖、契约、验收和验证预算明确。实现者可自主处理范围内细节；改变研究主张、数据访问或公共接口时回到相应设计评审。

### 7.3 标签与里程碑

初期控制数量：`type:feature/bug/refactor/experiment/design`、`area:data/model/eval/infra/docs`、`priority:P0/P1/P2`。Epic 可加单独 `epic` 标签。只有需要时再细分模块标签，不为所有组合预建标签。

里程碑按可交付能力设定：基线可复现 → 主包与契约稳定 → 模块消融闭环 → 空间与迁移评估 → 单项深化。不要一开始按每周建大量里程碑。

### 7.4 工程 Issue 模板

```text
问题与期望行为
依据：相关 ADR、模块、原代码
范围：允许写入路径 / 不在范围内
依赖：Issue/PR；冻结的接口
实施步骤：最多几项可验收动作
验收：行为、测试、回归、文档
验证命令与预算
交付：PR、迁移说明或运行引用
```

### 7.5 实验 Issue 模板

```text
假设与可能被否定的条件
比较组与同容量/同预算控制
数据版本、划分、信息访问、目标域标签预算
代码提交、配置、种子与优化步数
选模规则和冻结的测试集合
指标与机制证据
运行预算与停止条件
结果清单、失败运行、结论及限制
```

PR 引用对应 Issue。工程验收成立才使用自动关闭语义；实验实施代码的合并只代表实验工具完成，不应顺手关闭尚未执行的实验 Issue。

### 7.6 PR 完成定义

- scope 与 Issue 一致，额外改动有解释。
- 新模块关闭时回归到约定基线；公开接口变化有迁移说明。
- 相关数值/契约/集成检查通过，未执行检查明确记录。
- 配置、文档、checkpoint 或结果 schema 的相关引用同步更新。
- 未混入本机路径、真实数据、生成权重和非任务文件。
- 测试与评价证据来自可定位记录；不把合成通过写成精度提升。
- 关键协议、公共契约与结论由独立评审检查；最终合并权限由仓库维护规则决定。

## 8. 测试、持续验证与研究记录

### 8.1 检查分层

| 层次 | 每次相关 PR | 后续扩展 |
|---|---|---|
| 静态/文档 | 格式、导入、链接、配置 schema、模块索引 | 依赖方向检查 |
| 数值单元 | 小张量、空区域、归一化、梯度 | 新算子极端输入 |
| 契约 | 输入形状、标签访问、模式、序列化 | 共享头和新协议 |
| 集成 | 合成训练/保存/加载/评价/导出 | 多配置配对组合 |
| 回归 | 基线、共有初始化、旧权重迁移 | 版本间对照 |
| 真实实验 | 不默认每次 PR 运行 | 依据实验 Issue，按资源排程 |

保留现有 18 项合成回归作为迁移起点，拆分时保持覆盖而非只增加测试数量。基线行为、梯度和配置恢复比文件是否成功移动更重要。

分支保护建议在快速检查稳定后启用：主要分支通过 PR 合并、必要检查通过、关键区域得到对应评审。具体启用规则和实际账号在评审后确定，本轮不修改设置。

### 8.2 结果与大文件

`runs/<run_id>/` 包括解析后配置、代码版本/dirty 状态、数据与划分指纹、随机种子、训练历史、权重、预测、指标和诊断。共享结果报告只保存可公开的小型摘要与产物清单，引用外部产物位置和校验值。

运行 ID 与 Issue/PR 关联，但不只用 Issue 号作为目录名：同一 Issue 可能多次运行。代码工作树有改动时记录具体源码哈希，不仅记录 Git SHA。

暂不强制引入 DVC/MLflow/W&B 等平台。先定义稳定的 run manifest 和文件协议，之后按协作需求加后端，不让实验读取依赖某个平台的界面。

配置 schema、run manifest 和 checkpoint 格式分别有版本；破坏性变化提供加载迁移或明确拒绝，不静默猜测。旧模型结果不能因新表格格式重新命名而变成新实验结果。

## 9. 渐进迁移策略

### 第一阶段：确认来源并建立基线

核实目标仓库 checkout、远端状态与源码来源。整理需要进入目标仓库的文件，保留现有未提交工作。建立可恢复基线快照与来源清单，记录源码哈希、已有测试和代表性旧权重配置。

### 第二阶段：先建规则与契约

评审目录、数据类型、配置、模块登记、Issue/PR 模板与完成定义。只建立近期需要的目录。文档迁移时保留研究材料原始来源和草案状态，不把旧对话中的建议当作已批准架构。

### 第三阶段：迁移一条完整的基线链路

先把 VCA→共享特征→learned Q/A→双分支→固定融合→分类→保存/评价迁到主包，建立端到端合成示例。每个迁移 PR 以行为保持为目标，不夹带新模型算法。

### 第四阶段：逐个接入已有插件

迁移对齐、交互、边重加权及现有消融预设。配置和旧入口调用统一工厂。通过关闭回归、梯度与保存恢复后，再开始新增区域残差等研究机制。

### 第五阶段：清理兼容入口与推进研究

旧入口在至少一个明确迁移周期后，根据验收结果删除或保留薄包装。来源不明的临时脚本、会议材料和旧产物先分类归档，不批量删除研究工作区，也不直接上传所有文件。

A01 → A02/A03 → A04/A05/A06
                   ↓
                  B01 → B02/B03

示例：契约稳定后，一个开发者做残差模块，一个做数据协议，一个迁移基线。集成负责人单独写 factory/backbone/config/schema 的共享改动；评审者读取各分支并核验证据。并行数量由独立范围和资源决定，不以智能体数量作为进度指标。

## 12. 本轮建议讨论并评审的六项决策

| 决策 | 推荐方案 | 需要权衡 |
|---|---|---|
| 仓库组织 | 单仓库＋单主包 `src/hsi` | 根脚本保留多久、是否接受包名 |
| 迁移方式 | 来源清单＋基线回归＋分 PR 渐进迁移 | 短期包装成本与长期重复逻辑风险 |
| 文档语言 | 中文叙述＋英文标识符，简短英文入口按需 | 对外贡献者与维护成本 |
| 任务状态 | GitHub Issue/Project 为唯一权威 | 没有 Projects 时用简化流程 |
| 协作边界 | 独立工作树＋路径负责人＋集中共享接口集成 | 接口区会成为需要排程的串行步骤 |
| 首个里程碑 | 先基线可复现和模块闭环，再新增复杂机制 | 前期整理投入与后续实验可信度 |

评审本草案后，先从 A01/A02、必要协作约定与主工作清单 P0 提取一小批可执行 Issue。A03—A06 和 B01 按研究推进需要逐步完成，不要求先落实整个目标目录才允许开发研究模块。其余条目作为主清单的派生路线图，随着接口和研究证据细化，不一次性创建大量缺少上下文的任务。
