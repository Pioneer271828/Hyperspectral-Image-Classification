# M5 动态新增任务头状态继承验收

日期：2026-11-02；[Issue #66](https://github.com/Pioneer271828/Hyperspectral-Image-Classification/issues/66)、[PR #67](https://github.com/Pioneer271828/Hyperspectral-Image-Classification/pull/67)，对应当前整改清单 AUDIT-2。

## 改了什么、有什么用

新增任务的三个分类头继承对应头族的设备和 dtype，空头族回退到 backbone；运行模式继承外层模型。新域 BatchNorm1d/2d 继承所属归一化包装器的设备、dtype 和 train/eval 状态，同时保留全新的默认仿射参数及运行统计。旧任务参数、缓冲、运行状态和构造时预先建头的行为不变。

这使已经迁到 GPU 或切换为 eval 的模型可以继续注册传感器/任务，避免新头仍在 CPU、推理时新归一化层误更新统计。外层 train、backbone eval 等混合模式也按各自拥有者继承，不能通过全模型调用 train/eval 来“修复”而破坏原冻结策略。

注册函数不持有优化器。调用方须在注册后构建优化器，或按参数身份差集显式加入新头及新域归一化参数；指南给出保留旧优化器状态的用法。测试使用已有 Adam，加入新增参数后跑两步，确认三头权重和新域参数实际更新，源任务专属参数保持不变。

## 是否真的修复了问题

用 Git 读取的基准实现替换相同夹具中的模型和域归一化类，分别运行“头继承”“归一化继承”“混合运行状态”三项测试方法：CPU 产生 16 个预期失败子案例，CUDA 产生 21 个，均为 3 项测试方法、0 个运行错误。失败日志完整保留，证明测试能够检出旧错误。

直接在已迁移、float64、eval 的模型上注册新任务，结果为：

| 项目 | 修复前 | 修复后 |
|---|---|---|
| GPU 模型新增头位置 | CPU | CUDA |
| 新头和新域 dtype | float32 | float64 |
| 新头 training | true | false |
| 5 个新域归一化层 training | 全 true | 全 false |

首版实现的 CPU 测试已 9/9 通过，但 GPU 两项学习图输出逐位比较失败，最大差约 `1.4901161e-08`。随后对完全未注册新任务、无优化器、参数与缓冲哈希不变的同一 eval 模型，用同一种子输入重复 12 次，复现了同量级差异；CNN 输出不变，融合/图输出出现该差值。证据为首轮目录的 `unchanged-model-repeat-probe.json`。

据此仅将 CUDA learned 路径的预测比较改为 `rtol=1e-6, atol=1e-7`，CPU/静态路径与所有参数/缓冲比较保持严格相等；实现未改。首轮失败、诊断、测试修订提交及第二轮全部结果均保留，不把首轮记为通过。

## 限制、建议与交付停止点

工程正确性已验证，尚无新的真实数据精度结论。现有 G3 在迁移设备前预先建头，因此本修复不直接解释其精度；建议作为后续增加传感器/任务的基础修复纳入整合评审。

非默认 dtype 验证覆盖分类头及归一化单元；完整模型沿用 float32，未扩展整个图/adapter 的任意 dtype 支持。checkpoint 沿用原有默认 dtype 重建、返回 eval 的语义，不保存任意运行模式/混合 dtype。新参数默认可训练，已有冻结策略须由调用方明确应用；既有优化器、DDP 和编译图不会自动迁移。详见[动态注册契约](../../docs/guides/backbone-stages.md)。
